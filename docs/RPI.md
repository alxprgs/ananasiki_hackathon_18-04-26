# Raspberry Pi 4B + Raspberry Pi OS Lite (64-bit): первичная настройка и безопасное подключение

Этот файл описывает практический сценарий первоначальной настройки `Raspberry Pi 4 Model B` с `Raspberry Pi OS Lite (64-bit)` без монитора и клавиатуры, когда основной способ работы с платой - удалённый доступ по `SSH`.

Главная идея простая:

1. Ещё до первого запуска подготовить систему через `Raspberry Pi Imager`.
2. Сразу задать `hostname`, локализацию, пользователя, Wi-Fi и SSH.
3. После первого входа обновить систему.
4. Обязательно установить `ufw`, открыть SSH-порт и только потом включить firewall.
5. Перевести SSH на вход по публичным ключам и по возможности отключить вход по паролю.

## Что понадобится

- `Raspberry Pi 4B`
- блок питания для `Raspberry Pi 4`
- `microSD`
- компьютер с `Raspberry Pi Imager`
- доступ к вашей Wi-Fi сети
- SSH-клиент на основном компьютере

На современных `Windows`, `macOS` и `Linux` SSH-клиент обычно уже есть.

## Короткий чек-лист

Если нужен самый короткий сценарий:

1. В `Raspberry Pi Imager` выбрать `Raspberry Pi 4` и `Raspberry Pi OS Lite (64-bit)`.
2. В окне настроек задать:
   - `hostname`
   - локализацию
   - пользователя
   - Wi-Fi
   - `SSH`
3. Лучше сразу выбрать `Use public key authentication`.
4. После первого входа выполнить:

```bash
sudo apt update
sudo apt full-upgrade -y
sudo apt install -y ufw
```

5. Разрешить SSH в `ufw` до включения firewall.
6. Проверить вход по ключу.
7. При необходимости сменить SSH-порт.
8. Только после проверки отключать парольный вход.

## 1. Подготовка microSD через Raspberry Pi Imager

### Что выбрать в Imager

В `Raspberry Pi Imager` выбери:

- `Device` -> `Raspberry Pi 4`
- `OS` -> `Raspberry Pi OS Lite (64-bit)`
- `Storage` -> нужную `microSD`

После этого нажми `Next` и открой настройки кастомизации ОС.

## 2. Что обязательно заполнить в настройках Imager

### 2.1. Hostname

`Hostname` - это сетевое имя твоей Raspberry Pi.

Примеры хороших имён:

- `rescue-rpi-01`
- `robot-pi`
- `rpi4-maze`

Рекомендации:

- используй только латинские буквы, цифры и дефисы;
- не используй пробелы, подчёркивания и кириллицу;
- не оставляй стандартное имя вроде `raspberrypi`, если в сети может быть несколько плат.

Зачем это нужно:

- плату проще найти в роутере;
- по `mDNS` можно подключаться как к `hostname.local`;
- в логах и SSH-сессиях сразу понятно, к какому устройству ты подключён.

Пример:

```text
Hostname: rescue-rpi-01
```

Тогда потом подключение часто выглядит так:

```bash
ssh robot@rescue-rpi-01.local
```

### 2.2. Локализация

В разделе `Localisation` обычно задают:

- `Time zone`
- `Keyboard layout`
- `Wi-Fi country`

Для примера:

```text
Time zone: Europe/Moscow
Keyboard layout: us / ru
Wi-Fi country: RU
```

Почему это важно:

- правильный часовой пояс нужен для логов, cron-задач, сертификатов и отладки;
- корректная раскладка важна даже на Lite-образе, если ты иногда работаешь с платой локально;
- страна Wi-Fi влияет на разрешённые каналы и мощность, без неё сеть может вести себя нестабильно или вообще не подняться.

Если ты настраиваешь плату для другой страны, обязательно укажи именно её, а не оставляй "как попало".

### 2.3. Пользователь

В актуальных выпусках `Raspberry Pi OS` не стоит рассчитывать на старый шаблон с пользователем `pi`. Лучше сразу создать собственного администратора.

Пример:

```text
Username: robot
Password: очень-длинный-уникальный-пароль
```

Рекомендации:

- имя пользователя делай коротким и понятным;
- лучше использовать только `lowercase`, цифры и дефис;
- пароль должен быть уникальным и не использоваться больше нигде;
- не используй старый пароль `raspberry`.

Даже если ты планируешь вход только по ключам, пользователь и пароль всё равно нужны:

- для локального входа по консоли;
- для `sudo`;
- как аварийный вариант на время первичной настройки.

### 2.4. Wi-Fi сеть

В разделе `Wi-Fi` задай:

- `SSID`
- пароль
- тип сети: защищённая или открытая
- `Hidden SSID`, если сеть скрытая

Пример:

```text
SSID: MazeNet
Password: SuperSecretWifiPassword
```

Практические советы:

- самый надёжный вариант для headless-старта - прописать Wi-Fi сразу в Imager;
- внимательно проверь регистр символов в имени сети и пароле;
- если сеть скрытая, обязательно включи `Hidden SSID`;
- если есть возможность, на первый запуск полезно иметь запасной вариант через Ethernet.

### 2.5. SSH

В разделе `Remote Access` включи `SSH`.

Есть два варианта:

#### Вариант A. `Use password authentication`

Подходит для самого первого старта, если ключей ещё нет.

Плюсы:

- быстро;
- просто;
- можно подключиться сразу.

Минусы:

- менее безопасно;
- пароль потом всё равно лучше отключить.

#### Вариант B. `Use public key authentication`

Это предпочтительный вариант.

Если у тебя уже есть публичный ключ, вставь его сразу в Imager. Тогда плата с первого запуска будет готова к входу по ключу.

Если ключа ещё нет, можно:

1. сначала включить вход по паролю;
2. после первого подключения добавить ключ;
3. затем отключить парольный вход.

## 3. Первый запуск Raspberry Pi

После записи образа:

1. вставь `microSD` в Raspberry Pi;
2. подключи питание;
3. подожди `1-3` минуты на первый старт;
4. дождись подключения к Wi-Fi.

Если образ уже был настроен через Imager, то на этом этапе плата обычно уже:

- получила hostname;
- создала пользователя;
- подняла SSH;
- попыталась подключиться к Wi-Fi.

## 4. Как найти Raspberry Pi в сети

### Способ 1. Через `hostname.local`

Если `mDNS` работает, попробуй:

```bash
ping rescue-rpi-01.local
```

или сразу:

```bash
ssh robot@rescue-rpi-01.local
```

Это самый удобный вариант для домашней или лабораторной сети.

### Способ 2. Через список устройств на роутере

Если `.local` не резолвится:

1. зайди в веб-интерфейс роутера;
2. открой список подключённых устройств;
3. найди устройство по `hostname` или MAC-адресу;
4. возьми IP.

После этого подключайся так:

```bash
ssh robot@192.168.1.50
```

### Способ 3. Через локальное сканирование сети

Если роутер неудобный, можно искать устройство по локальной сети с другого компьютера. Но в обычной практике проще всего использовать:

- `hostname.local`
- либо список устройств в роутере

## 5. Первое SSH-подключение

Примеры:

```bash
ssh robot@rescue-rpi-01.local
ssh robot@192.168.1.50
```

При первом входе система спросит подтверждение fingerprint. Это нормально.

После подключения полезно сразу проверить базовые вещи:

```bash
hostnamectl
timedatectl
ip -br a
systemctl status ssh
```

## 6. Что сделать сразу после первого входа

Сразу после первого успешного подключения:

```bash
sudo apt update
sudo apt full-upgrade -y
sudo reboot
```

После перезагрузки подключись снова.

Дальше логика такая:

1. настроить SSH-ключи;
2. при желании сменить порт SSH;
3. установить и настроить `ufw`;
4. только после проверки отключить парольный вход.

Именно в таком порядке меньше шанс случайно отрезать себе доступ.

## 7. Настройка входа по SSH-ключам

### 7.1. Создание ключа на основном компьютере

Если ключей ещё нет, создай их на своём основном компьютере:

```bash
ssh-keygen -t ed25519 -C "robot-laptop"
```

Рекомендуется:

- использовать `ed25519`;
- задать passphrase для приватного ключа;
- хранить приватный ключ только на своём компьютере.

Обычно получаются файлы:

- приватный ключ: `~/.ssh/id_ed25519`
- публичный ключ: `~/.ssh/id_ed25519.pub`

### 7.2. Передача публичного ключа на Raspberry Pi

Если на клиенте есть `ssh-copy-id`, то проще всего так:

```bash
ssh-copy-id robot@rescue-rpi-01.local
```

или по IP:

```bash
ssh-copy-id robot@192.168.1.50
```

Если `ssh-copy-id` нет, можно сделать вручную.

На Raspberry Pi:

```bash
mkdir -p ~/.ssh
chmod 700 ~/.ssh
touch ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
```

Потом добавь содержимое своего публичного ключа в:

```text
~/.ssh/authorized_keys
```

Одна строка = один публичный ключ.

### 7.3. Проверка входа по ключу

После копирования ключа обязательно проверь, что вход работает:

```bash
ssh robot@rescue-rpi-01.local
```

или:

```bash
ssh robot@192.168.1.50
```

Если вход по ключу работает, только теперь можно переходить к ужесточению SSH.

## 8. Смена SSH-порта

Менять порт SSH не обязательно, но это нормальная дополнительная мера против лишнего шума в логах и автоматических переборов.

Важно:

- смена порта не заменяет SSH-ключи;
- смена порта не заменяет firewall;
- не меняй порт, пока не проверил обычный вход по SSH.

### 8.1. Редактирование конфигурации SSH

Сделай резервную копию:

```bash
sudo cp /etc/ssh/sshd_config /etc/ssh/sshd_config.bak
```

Открой конфиг:

```bash
sudo nano /etc/ssh/sshd_config
```

Например, поменяй:

```text
Port 2222
```

Дополнительно можно привести конфиг к такому виду:

```text
Port 2222
PermitRootLogin no
PubkeyAuthentication yes
AuthorizedKeysFile .ssh/authorized_keys
```

Пока не отключай `PasswordAuthentication`, если ещё не проверил новый порт.

### 8.2. Проверка синтаксиса и перезапуск

Перед рестартом SSH проверь конфиг:

```bash
sudo sshd -t
```

Если ошибок нет:

```bash
sudo systemctl restart ssh
```

Теперь подключайся уже так:

```bash
ssh -p 2222 robot@rescue-rpi-01.local
```

или:

```bash
ssh -p 2222 robot@192.168.1.50
```

Очень важно:

- не закрывай текущую SSH-сессию, пока не проверишь новую;
- сначала открой вторую сессию на новом порту;
- только после успешного входа считай изменение порта завершённым.

## 9. Обязательная установка и настройка UFW

После первого входа `ufw` действительно стоит поставить обязательно.

### 9.1. Установка

```bash
sudo apt install -y ufw
```

### 9.2. Базовые политики

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
```

### 9.3. Разрешение SSH до включения firewall

Это критичный момент.

Нельзя делать так:

1. включить `ufw`;
2. и только потом вспоминать про SSH.

Можно потерять текущий доступ.

#### Если оставляешь стандартный порт `22`

```bash
sudo ufw allow OpenSSH
```

или:

```bash
sudo ufw allow 22/tcp
```

Ещё лучше - ограничение скорости:

```bash
sudo ufw limit 22/tcp
```

#### Если поменял SSH, например, на `2222`

```bash
sudo ufw allow 2222/tcp
```

или:

```bash
sudo ufw limit 2222/tcp
```

Важно:

- профиль `OpenSSH` обычно соответствует стандартному порту `22`;
- если у тебя нестандартный порт, открывай именно его явно.

### 9.4. Включение firewall

Когда правило уже добавлено:

```bash
sudo ufw enable
sudo ufw status verbose
```

Если ты уже сидишь по SSH, внимательно прочитай предупреждение и убедись, что нужный порт открыт.

### 9.5. Удаление старого порта после миграции

Если ты ушёл с `22` на `2222`, а новый порт уже проверен, старое правило можно удалить:

```bash
sudo ufw delete allow 22/tcp
```

или:

```bash
sudo ufw delete limit 22/tcp
```

### 9.6. Дополнительное усиление правил

Если доступ нужен только из локальной сети, можно ограничить источник:

```bash
sudo ufw allow from 192.168.1.0/24 to any port 2222 proto tcp
```

Это уже строже, чем просто открыть порт всему миру.

## 10. Отключение парольного входа в SSH

Делать это нужно только после того, как:

1. вход по ключу уже проверен;
2. новый порт, если ты его менял, уже проверен;
3. `ufw` уже разрешает нужный SSH-порт.

Открой конфиг:

```bash
sudo nano /etc/ssh/sshd_config
```

Приведи важные строки к такому виду:

```text
PermitRootLogin no
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
AuthorizedKeysFile .ssh/authorized_keys
```

Проверь конфиг:

```bash
sudo sshd -t
```

Перезапусти SSH:

```bash
sudo systemctl restart ssh
```

И снова обязательно проверь вход новой отдельной сессией:

```bash
ssh -p 2222 robot@rescue-rpi-01.local
```

или, если порт не менялся:

```bash
ssh robot@rescue-rpi-01.local
```

## 11. Как менять настройки после установки

### 11.1. Hostname

Самый удобный штатный вариант:

```bash
sudo raspi-config
```

Дальше:

```text
System Options -> Hostname
```

Либо через команду:

```bash
sudo raspi-config nonint do_hostname rescue-rpi-01
```

После смены hostname лучше:

- переподключиться по новому имени;
- проверить `hostnamectl`;
- помнить, что адрес станет вида `new-hostname.local`.

### 11.2. Локаль, timezone, keyboard и Wi-Fi country

Через интерактивный инструмент:

```bash
sudo raspi-config
```

Дальше:

```text
Localisation Options
```

Полезные команды:

```bash
sudo raspi-config nonint do_change_locale ru_RU.UTF-8
sudo raspi-config nonint do_change_timezone Europe/Moscow
sudo raspi-config nonint do_wifi_country RU
```

Для раскладки клавиатуры удобнее использовать интерактивный режим `raspi-config`, потому что код конкретной раскладки зависит от выбранной схемы.

### 11.3. Пользователь

Если нужно создать нового пользователя уже после установки:

```bash
sudo adduser robot2
sudo usermod -aG sudo robot2
```

Дальше:

1. скопируй SSH-ключи новому пользователю;
2. проверь вход под новым пользователем;
3. только потом при необходимости удаляй старого.

Удаление старого пользователя:

```bash
sudo deluser --remove-home olduser
```

Перед удалением обязательно убедись, что новый пользователь:

- умеет входить по SSH;
- входит в группу `sudo`;
- действительно работает.

### 11.4. Wi-Fi после установки

Самый удобный и безошибочный путь для headless-сценария - задать Wi-Fi заранее через Imager.

Если менять сеть уже на запущенной системе, в актуальных выпусках Raspberry Pi OS обычно используют штатные инструменты сетевого менеджера, например:

- `nmtui`
- `nmcli`

Но если задача простая и плата ещё не введена в эксплуатацию, часто быстрее и надёжнее:

1. перепрошить или перезаписать образ через Imager;
2. заново прописать корректные параметры Wi-Fi;
3. исключить ручные ошибки в SSID и пароле.

### 11.5. SSH

Для управления SSH в рабочей системе полезны команды:

```bash
sudo systemctl status ssh
sudo systemctl restart ssh
sudo sshd -t
ss -tulpn | grep ssh
```

Если SSH не был включён заранее, можно включить его так:

```bash
sudo systemctl enable --now ssh
```

## 12. Аварийный headless-сценарий, если забыл включить SSH до первого запуска

Если образ уже записан, но настройки в Imager не были сделаны, можно ещё до первого старта поправить `bootfs`.

### 12.1. Включить SSH

В корне первого раздела карты памяти создай пустой файл:

```text
ssh
```

Без расширения.

### 12.2. Создать пользователя вручную

В корне того же раздела создай файл:

```text
userconf.txt
```

Внутри одна строка:

```text
<username>:<encrypted-password>
```

Хэш пароля можно получить на другом Linux/macOS-хосте так:

```bash
openssl passwd -6
```

Потом вставь результат в `userconf.txt`.

Это полезный запасной вариант, если:

- Imager не использовался;
- образ был записан сторонним софтом;
- нужно срочно оживить headless-доступ.

## 13. Рекомендуемая безопасная последовательность действий

Если нужен именно безопасный и практичный порядок, то он такой:

1. Прошить карту через Imager.
2. Сразу задать `hostname`, локализацию, пользователя, Wi-Fi и `SSH`.
3. Войти по SSH.
4. Обновить систему.
5. Настроить вход по ключу.
6. При желании сменить SSH-порт.
7. Установить `ufw`.
8. Разрешить нужный SSH-порт в `ufw`.
9. Включить `ufw`.
10. Только после всех проверок отключить `PasswordAuthentication`.

Это самый важный раздел всего документа: именно порядок шагов спасает от ситуации "я всё защитил и больше не могу войти".

## 14. Типовая минимально безопасная конфигурация

Пример рабочей логики:

- пользователь: `robot`
- hostname: `rescue-rpi-01`
- SSH-порт: `2222`
- вход: только по ключам
- root по SSH: запрещён
- `ufw`: включён, разрешён только `2222/tcp`

### Пример `sshd_config`

```text
Port 2222
PermitRootLogin no
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
AuthorizedKeysFile .ssh/authorized_keys
```

### Пример правил `ufw`

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw limit 2222/tcp
sudo ufw enable
sudo ufw status verbose
```

### Подключение после этого

```bash
ssh -p 2222 robot@rescue-rpi-01.local
```

## 15. Частые ошибки

### Ошибка 1. Включили `ufw`, не открыв SSH

Результат: доступ по сети пропадает.

Правильно:

1. сначала добавить правило на SSH;
2. потом включать `ufw`.

### Ошибка 2. Отключили `PasswordAuthentication`, не проверив ключ

Результат: вход невозможен.

Правильно:

1. скопировать ключ;
2. войти по ключу;
3. только потом отключать пароль.

### Ошибка 3. Сменили SSH-порт и сразу закрыли текущую сессию

Результат: если порт настроен с ошибкой, доступ потерян.

Правильно:

1. оставить текущую сессию открытой;
2. открыть вторую сессию на новом порту;
3. проверить вход;
4. только потом завершать старую.

### Ошибка 4. Оставили стандартный слабый пароль

Результат: даже при нестандартном порте это остаётся плохой практикой.

Правильно:

- сильный уникальный пароль;
- затем переход на SSH-ключи;
- затем отключение пароля в SSH.

### Ошибка 5. Не задали `Wi-Fi country`

Результат: сеть может не работать так, как ожидается, особенно на части каналов.

Правильно:

- выставлять реальную страну эксплуатации.

## 16. Итог

Для `Raspberry Pi OS Lite` лучший путь такой:

- максимум настроек сделать ещё в `Raspberry Pi Imager`;
- сразу дать плате нормальный `hostname`;
- заранее создать своего пользователя;
- прописать Wi-Fi и включить SSH;
- после первого входа немедленно обновить систему;
- установить `ufw` и открыть SSH-порт до его включения;
- настроить вход по публичным ключам;
- по желанию перенести SSH на другой порт;
- в конце отключить парольный вход.

Если всё сделать именно в этом порядке, получится удобная и заметно более безопасная стартовая конфигурация для headless-Raspberry Pi.
